### Fixed

- **`@reticlehq/server`: a Harness journey is no longer failed by its own early look.** The Harness asserted the text a button produces before the request behind it had answered, read `no`, and failed a journey whose goal was met, while the same assert held a second later. A passive check that the same claim later proves is superseded, in the drive's count and in the run's verdict alike, so the answer and the dashboard agree. A declared check (`reticle_act_and_wait { until }`) that failed still fails: a first click that did nothing is a finding even if a second one works.
- **`@reticlehq/engine`: a claim about the page that misses while a write is still open is `unknown`, not `no`.** The outcome is not in yet. A claim about the network keeps its own rule, so a request that never fired beside an unrelated open write is still a miss.
- **`@reticlehq/server`: a journey step no longer reports its own answered request as "still in flight".** `reticle_act { steps }` described each step over the instant it dispatched, before the wait its verdict came from, so a step that waited for its declared `200` carried a `request-never-settled` contradiction about that same request beside `held: true`.
- **`@reticlehq/server`: a drifted replay no longer advises rebinding to an unrelated control.** A replay that started signed out missed `compose-prompt` on the login screen and suggested `login-submit` as "the closest survivor". A survivor is offered only when it is close enough to be a rename; otherwise the advice names a start state the recording did not have.
- **`@reticlehq/server`: a locked Harness is no longer reported as a possible Reticle defect.** The platform's "Harness is locked. Setup score: …" was answered with an invitation to file a bug report; it now gets the steps that unlock it.
- **`@reticlehq/server`: a bare `settled` wait no longer invites a bug report.** Its `unknown` means nothing real was asserted, which is the caller's to fix, and it was answered "an unknown verdict is our defect, not yours".
- **`@reticlehq/server`: a replay that drove a journey to its end now proves it, with no model.** When a journey's replays decided nothing (a flow that checked no end), the Harness re-drove the goal from the start even when the page already showed the end the replay had reached, and on an app whose start signs you out the re-drive failed a working app. The end the goal quotes is now checked where the replay left it, and is never credited when the page showed it before the journey ran.
- **`@reticlehq/server`: the Harness reads a journey's end after the request that writes it has answered.** Its settle only saw requests that started after the look began, so a drive that ended on "Generating…" was read a second too early.
- **`@reticlehq/server`: a Harness plan is proved only when no journey was left undecided.** A plan with one passed journey beside journeys a credit cut-off had blocked read PROVED, and its result block was retitled "proved". A plan now needs every journey passed (or a side road deliberately not taken); anything else short of a failure reads not proved.
- **`@reticlehq/server`: one rule decides which early checks a later pass supersedes, everywhere.** The Harness's tally, a run's verdict, a synced run's flow status and the session's result block each applied their own version, and one applied none, so an end-of-session answer could say `claim: pass` beside "Reticle result: failed".
- **A run with a failed check beside a passed one is a fail, not a partial.** The result block, the CLI and the platform already called it a fail; the run file said partial. A partial is now only a pass with something skipped or undecided beside it.
- **`@reticlehq/server`: a Harness drive stops at the end its goal names.** A drive that reached "Generated script for" kept going until its step budget ran out, navigated to a start page that signs the app out, and ended on a page without the result, failing a journey that worked. Once a check has held and the page shows the end the goal quotes, the drive stops there.
- **`@reticlehq/server`: a platform refusal is recognised by its code, not its wording.** The platform reworded its Harness lock and every locked Harness came back as "may be a defect in Reticle". A refusal's code (`harness_locked`, `harness_off`, `needs_card`) now picks a lead sentence Reticle owns, and that is what is recognised.

### Added

- **`reticle setup` signs a Tauri dev build with your signing identity, so macOS stops asking for the keychain password.** macOS ties keychain items to the signature of the app that saved them, and a `tauri dev` build is ad-hoc signed, so every keychain read asked for the password. When `APPLE_SIGNING_IDENTITY` or `bundle.macOS.signingIdentity` is set, the dev build Reticle starts is signed with that identity and the app's bundle identifier before it runs (through Cargo's runner, since `tauri dev` itself ignores the identity). Nothing changes without an identity, off macOS, or when the project already sets a Cargo runner; a signing failure is said and never stops the app.
